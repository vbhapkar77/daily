# Password hashes and reset-token hashes

> Passwords need a deliberately slow, salted hash. Random reset tokens need enough entropy and can be stored as a fast SHA-256 digest.

## How Daily uses this

- `backend/src/main/java/com/vishalbhapkar/daily/lib/auth/PasswordHasher.java` uses bcrypt cost 12. Hashing the same password twice produces different values because bcrypt includes a random salt. Login checks a password with `verify`, not string equality.
- `backend/src/main/java/com/vishalbhapkar/daily/lib/auth/SecureTokens.java` generates 32 random bytes (256 bits) and encodes them as a URL-safe string.
- `backend/src/main/java/com/vishalbhapkar/daily/lib/auth/TokenHasher.java` stores a SHA-256 digest of that token. The plain token is sent to the user and is never stored in the database.

## Why use different hashes?

Human passwords are often guessable. A database leak lets an attacker try candidates offline, so bcrypt makes each guess expensive. A reset token is generated by `SecureRandom` and has 256 random bits; guessing it is impractical if those bits stay secret. SHA-256 lets the server look up a presented token without storing the original bearer secret.

## Interview framing

**Q: Why not hash passwords with SHA-256?** A fast digest makes offline password guessing cheap. Use a password hashing function such as bcrypt with an appropriate work factor.

**Q: Why can reset tokens use SHA-256?** They are high-entropy random values rather than user-chosen strings. The database keeps only the digest, while the plain token is delivered to the user.
